# Android native layer — CLAUDE.md

Applies to `MainActivity.kt`, `SecondaryAppsPresentation.kt`, and the Android manifests.
Moved out of the root `CLAUDE.md` so it loads when you work under `android/` rather than in every session.

**The bottom screen is a separate Android window, so `MainActivity`'s input rules do not reach it.** `SecondaryAppsPresentation` extends `android.app.Presentation`, which is a `Dialog`: cancelable and focusable by default. Tapping the bottom screen focuses that window, and BACK then runs `Dialog.cancel()` -> `FlutterPresentation.dismiss()`, which destroys the secondary engine — the bottom half of the launcher is gone until the app restarts while the top half keeps running. `MainActivity.dispatchKeyEvent`/`onBackPressed` swallow BACK for their own window only. The presentation is therefore `setCancelable(false)` + a BACK-swallowing `dispatchKeyEvent` + `FLAG_NOT_FOCUSABLE`; the last one also stops the bottom display becoming the *top-focused display*, which is what sent HOME (and gamepad keys) to the wrong screen. That is only safe while the secondary UI stays touch-only — it has no text fields or key handling today.

**Reproducing it needs NeoStation set as the default launcher, after a reboot.** Otherwise BACK on that window takes Android 13's predictive-back path, which logs `CoreBackPreview: startBackNavigation ... backType=TYPE_UNDEFINED` and no-ops — so the bug looks random, and neither `adb shell input keyevent 4` nor an edge-swipe gesture reproduces it. As HOME it goes down the classic `KEYCODE_BACK` dispatch instead and dismisses. In logcat the kill is `FvpPlugin: onDetachedFromEngine` -> `ViewRootImpl: doDie` -> `CoreBackPreview: Window{...}: Setting back callback null`, followed by `InputEventReceiver: Attempted to finish an input event but the input event receiver has already been disposed` (a window torn down mid-input-event). On the AYN Thor the bottom screen is **display 4**, and Quickstep's `SecondaryDisplayLauncher` already runs behind the presentation — it is revealed by the dismissal, not launched by it.

**A dock-launched app is revealed by *hiding* that presentation, and the hide looks exactly like the app closing.** `MainActivity.hideSecondaryForApp` hides the panel and arms `ScreenshotAccessibilityService`'s watch, which restores it when the bottom display goes back to its home/launcher (Android gives a normal app no other signal that a window on another display was dismissed). But hiding the panel uncovers `com.android.launcher3/.secondarydisplay.SecondaryDisplayLauncher` sitting behind it and fires `TYPE_WINDOWS_CHANGED` before the launched app has drawn, so a plain "top window on that display is a launcher -> restore" test fires ~40ms after the launch and puts the panel straight back over the app: it flashes and is gone, while `dumpsys activity activities` still shows the app as `topResumedActivity` on display 4 (it was never killed, just covered). The watch is therefore two-phase — it arms only once a non-home window has taken that display — plus a 10s watchdog in `MainActivity` for a launch that never lands, and `onResume` must not restore while a watch is armed: a dock app runs on the *other* display, so this activity resuming says nothing about whether it closed. Both the watch and the watchdog are armed **only when the service can actually watch** (`startWatch` returns false when it isn't connected or on pre-R, where `windowsOnAllDisplays` is unavailable): armed blind, the watchdog would just drop the panel onto the running app at its timeout, and `onResume` would never restore. Without the service the old resume-based restore is the fallback.

**A game launched on the other screen never pauses `MainActivity`, so its session is not bracketed by `onPause`/`onResume`.** The per-system/per-game launch screen (`user_launch_display`, `LaunchDisplayService`) sends `launch_display` = `"primary"` (display 0) or `"secondary"` (first other display) with `launchGenericIntent`; with no setting nothing is sent and Android launches where it always did. When the resolved display is not this activity's, `startGameOnOtherDisplay` stamps `gameLaunchTimestamp` itself (onPause never does), hides the Now Playing presentation if the game lands on its display, and ends the session on whichever comes first: the accessibility watch seeing the game's window leave that display, or this activity regaining focus (`onTopResumedActivityChanged(true)`, the same edge Flutter reports as `AppLifecycleState.resumed`). Focus/resume edges in the first 5 s are treated as the handoff and ignored. Without the accessibility service, tapping NeoStation's screen mid-game ends the session (Flutter would close it on that edge anyway); with it, the watch is the reliable signal. `EmulatorLauncher.startOnDisplay` checks `isActivityStartAllowedOnDisplay` and falls back to a plain launch, so a refused display never blocks the game.
